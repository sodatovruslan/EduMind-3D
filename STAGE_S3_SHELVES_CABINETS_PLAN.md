## 1. Ключевое архитектурное открытие (нужно решить до кода)

Сегодня рендер контейнера **жёстко хардкодит высоту** на уровне стола:
`position={[item.position[0], 0.05, item.position[1]]}` (`ContainerMesh`), аналогично у
`StockBottleMesh`. `position: [number, number]` в `ContainerItem`/`StockBottle` — это X,Z СТОЛА,
третьего измерения нет вообще. Шкаф висит на высоте y≈1.8 — предмет "внутри шкафа" физически не
может быть представлен текущим типом данных.

**Решение (минимальное, не переписывающее X/Z-логику стола):** добавить предметам новое числовое
поле `elevation: number` (мировой Y), которое рендер использует ВМЕСТО захардкоженной константы:
`position={[item.position[0], item.elevation, item.position[1]]}`. Для существующих предметов на
столе `elevation` — просто те же самые числа, что уже были захардкожены (0.05 для сосудов,
аналогично для бутылок) — **нулевое визуальное изменение для beaker-1/test-tube-1/бутылок**.
Для `flask-1` (POC-предмет, который переезжает в шкаф) — `elevation` равен мировой высоте полки
внутри шкафа (~1.8).

Альтернатива (полноценный 3D `position: [number,number,number]` или discriminated union
`{type:"table"|"cabinet", ...}`) была рассмотрена и отклонена — она затронула бы `MOVE_ITEM`,
`SET_ITEM_TRANSFORM`, проверки границ стола и весь Stage S-2 без реальной необходимости: X/Z стола
и "в каком шкафу лежит предмет" — по сути разные оси одной и той же физической позиции, а не
разные системы координат.

**Обновлено по замечанию пользователя: принадлежность предмета шкафу — ЯВНОЕ поле, не только
вывод из геометрии.** Первая версия плана предлагала выводить принадлежность из совпадения
position/elevation с известным слотом. Пользователь справедливо указал, что для
детерминированного возврата, проверки занятости, будущих AI-событий/отчётов учителю и
устранения неоднозначности между соседними шкафами (два слота на одной высоте — координаты
одни, слот разный) чисто геометрический вывод недостаточен. Решение:

```ts
storageSlotId: string | null
```
на `ContainerItem`/`StockBottle`, рядом с `position`/`elevation`/`rotationY`. Правила (жёсткие,
проверяются тестами):
- предмет на столе или в руке — `storageSlotId === null`;
- предмет официально размещён в шкафу — `storageSlotId` содержит id конкретного слота (раздел 2);
- `pickUp()` (взятие из шкафа) атомарно освобождает слот: `storageSlotId → null` в том же
  диспатче, что переводит предмет в Held (иначе возможен момент, когда предмет одновременно
  "в руке" и "числится в слоте");
- возврат в шкаф атомарно задаёт `position`/`elevation`/`rotationY` слота И `storageSlotId`
  одним диспатчем `SET_ITEM_TRANSFORM` (расширенным, см. раздел 6) — не двумя отдельными
  действиями, чтобы не было промежуточного несогласованного состояния.

`findCabinetContainingPosition(position, elevation)` (раздел 1, исходная версия) остаётся в
`lib/cabinets.ts`, но теперь используется только как **геометрическая проверка для гейтинга
фокуса** (в помощь читаемости кода/дебагу, "по факту предмет физически там же, где слот") — НЕ
как источник истины о принадлежности. Источник истины — `storageSlotId`. Если они когда-либо
разойдутся (не должны, т.к. пишутся атомарно), приоритет у `storageSlotId`.

## 2. Шкаф — не "предмет", плюс универсальный Slot Registry

Шкаф — НЕ `canBeHeld` (это мебель, не берётся в руку). Ему нужен собственный, отдельный от
`INTERACTABLE_REGISTRY` реестр. **Обновлено по замечанию пользователя**: слоты — не поле внутри
`CabinetConfig` (как было в первой версии плана), а **отдельный, универсальный реестр слотов**,
не привязанный жёстко к "один слот = один шкаф" — это специально готовит почву для будущих
стадий (несколько слотов на шкаф, полки без дверей, разные типы хранения) без переписывания.

```ts
// lib/cabinets.ts
export interface CabinetConfig {
  displayName: string;
  worldPosition: [number, number, number]; // та же точка, что уже использует Room() для отрисовки
  doorHitboxSize: [number, number, number];
  doorOpenAngleRad: number; // например -1.9 (~110°)
}

export const CABINET_REGISTRY: Record<string, CabinetConfig> = {
  "cabinet-2": { ... } // см. раздел 7 про выбор конкретного шкафа
};

// lib/storage-slots.ts — универсальный Slot Registry (не только для шкафов;
// та же форма подойдёт для будущих открытых полок без дверей)
export interface StorageSlot {
  id: string;
  cabinetId: string; // к какому шкафу относится (может быть shelfId в будущем — см. ниже)
  shelfId?: string; // на будущее: несколько полок внутри одного шкафа; пусто = единственная полка
  position: [number, number]; // мировые X,Z
  elevation: number; // мировой Y
  rotationY: number; // ориентация предмета в слоте (обычно 0)
  radius: number; // допустимый размер предмета — переиспользует FOOTPRINT_RADIUS_BY_KIND
                   // из placement-surfaces.ts, тот же смысл, что уже есть у стола
  allowedKinds: string[]; // например ["flask", "beaker", "test_tube"] — что можно сюда положить;
                           // пустой список — "любой" (для POC: один слот, allowedKinds: ["flask"])
}

export const STORAGE_SLOT_REGISTRY: Record<string, StorageSlot> = {
  "cabinet-2-slot-1": {
    id: "cabinet-2-slot-1",
    cabinetId: "cabinet-2",
    position: [...], // см. раздел 7, после spike
    elevation: 1.8,
    rotationY: 0,
    radius: 0.32, // как у сосудов, см. FOOTPRINT_RADIUS_BY_KIND
    allowedKinds: ["flask"],
  },
};

export function getSlot(id: string): StorageSlot | null { ... }
export function findSlotsForCabinet(cabinetId: string): StorageSlot[] { ... }
export function isKindAllowedInSlot(slot: StorageSlot, kind: string): boolean {
  return slot.allowedKinds.length === 0 || slot.allowedKinds.includes(kind);
}
export function findCabinetContainingPosition(
  position: [number, number],
  elevation: number
): string | null { ... } // геометрическая проверка (раздел 1) — сверяет со всеми StorageSlot,
                          // возвращает cabinetId владельца ближайшего совпавшего слота
```

**Совместимость слота и предмета проверяется явно** (`isKindAllowedInSlot`) — при возврате в
шкаф нельзя положить предмет в произвольную точку объёма шкафа или в слот с несовместимым
`allowedKinds`; кандидат на возврат (раздел 4) обязан быть одновременно (а) свободным
(`storageSlotId` этого слота ни у кого не выставлен) и (б) совместимым по типу.

`cabinetPositions` (сейчас захардкожен ЛОКАЛЬНО внутри `Room()`) переносится в `lib/cabinets.ts`
как единый источник истины — `Room()` начинает импортировать оттуда те же 4 позиции для отрисовки
(координаты не меняются, значит визуально ничего не сдвинется) — небольшой, оправданный рефактор
(иначе интерактивная и визуальная система хранили бы две независимые копии одних и тех же чисел,
что почти гарантированно разъехалось бы при следующей правке).

## 3. Focus теперь бывает двух видов — `focusedKind`

`ChemistryInteractionProvider` получает `focusedKind: "item" | "cabinet" | null` рядом с
`focusedId`. Причина: `E` должен вести себя по-разному ("взять предмет" vs "открыть/закрыть
шкаф"), и уже существующее правило Stage S-1 "нельзя сфокусироваться на новом предмете, пока
держишь один" **должно применяться ТОЛЬКО к `kind: "item"`** — фокус на шкафу должен оставаться
доступным, даже когда что-то уже держишь в руке (иначе невозможно будет вернуть предмет обратно —
это и есть основной сценарий этой стадии).

```ts
setFocused(id: string, kind: "item" | "cabinet"): void
```
`useInteractable(id)` (для предметов) не меняется. Новый параллельный хук `useCabinetInteractable
(id)` — аналогичная единая точка входа, но читает `CABINET_REGISTRY`/`cabinets` state вместо
`INTERACTABLE_REGISTRY`.

## 4. Семантика `E` расширяется (не меняя уже одобренную для предметов/стола)

Порядок проверок внутри существующего `E`-обработчика:

1. **Если `heldId` задан** (что-то в руке):
   - если сфокусирован ОТКРЫТЫЙ шкаф → ищем среди его слотов (`findSlotsForCabinet`) первый, где
     одновременно: слот свободен (ни у одного предмета `storageSlotId` не равен этому слоту) И
     `isKindAllowedInSlot(slot, heldItem.kind)` — если такой есть → **вернуть предмет в шкаф**:
     атомарно через `SET_ITEM_TRANSFORM` пишет `position = slot.position`, `elevation =
     slot.elevation`, `rotationY = slot.rotationY`, **и `storageSlotId = slot.id`** одним
     диспатчем (раздел 1) — чистит held. Если совместимого свободного слота нет — как будто шкаф
     не сфокусирован, переходим к следующей проверке.
   - иначе (как в S-2) — если валидная точка на столе (`placementCandidate`) → подтвердить туда
     (при этом `storageSlotId` атомарно пишется в `null` — предмет больше не числится в шкафу).
   - иначе — no-op, предмет остаётся в руке (без изменений от S-2).
2. **Если НЕ держим** и сфокусирован ЗАКРЫТЫЙ шкаф → открыть (`onToggleCabinet(id)`).
   Если сфокусирован ОТКРЫТЫЙ шкаф (и никакой предмет не держим) → закрыть тем же колбэком
   (простой toggle, без отдельной клавиши).
3. **Если НЕ держим** и сфокусирован предмет (как в S-1) → взять — **но только если предмет
   ДОСТУПЕН** (см. раздел 5 — предмет внутри закрытого шкафа не фокусируется вообще, значит и
   не может попасть в эту ветку).

`Escape` не меняется по смыслу — как и в S-2, безусловно возвращает предмет в исходную точку
текущего pickup-цикла (будь то стол или шкаф), никогда не кладёт "куда-то ещё".

`onToggleCabinet` — новый опциональный проп `ChemistryInteractionProvider`, тот же паттерн, что
`onConfirmPlacement`: провайдер остаётся домен-агностичным, сам не пишет в
`ChemistryWorkspaceProvider`, только вызывает переданный колбэк.

## 5. Доступность предмета зависит от состояния шкафа

Предмет, у которого `storageSlotId !== null` (источник истины — поле, не геометрия, раздел 1),
смотрим слот через `getSlot(storageSlotId)` → `slot.cabinetId` → если у этого шкафа сейчас
`!isOpen` — **предмет не фокусируется вообще**: `useInteractable(id)` возвращает `capability:
null` (как если бы предмет вовсе не был в `INTERACTABLE_REGISTRY`), пока шкаф закрыт. Как только
шкаф открыт — предмет становится фокусируемым/берущимся как обычно, без каких-либо иных
изменений. (`findCabinetContainingPosition` тут не используется — это геометрический хелпер для
отладки/консистентности, не путь принятия решений в рантайме.)

Дополнительная защита (не строго обязательная, но дешёвая и правильная): дверь шкафа —
непрозрачная геометрия, стоящая физически ПЕРЕД содержимым, поэтому raycast на закрытую дверь
и так физически не долетает до предмета внутри — правило выше не полагается на это случайное
геометрическое совпадение, а проверяет `isOpen` явно.

## 6. Изменения в домене (`ChemistryWorkspaceProvider.tsx`) — все аддитивные

1. `ContainerItem`/`StockBottle` получают два новых поля: `elevation: number` (раздел 1) и
   `storageSlotId: string | null` (раздел 1, обновление по замечанию пользователя).
2. Новый срез состояния `cabinets: CabinetState[]`, `CabinetState = { id: string; isOpen: boolean }`.
3. Новое действие `TOGGLE_CABINET { id }` — переключает `isOpen` у одного шкафа, не трогает
   ничего больше.
4. `SET_ITEM_TRANSFORM` получает необязательные `elevation?: number` и `storageSlotId?: string |
   null` — если не переданы, ведёт себя ТОЧНО как в S-2 (текущая высота стола, `storageSlotId` не
   трогается/остаётся `null`, обратная совместимость с уже написанным кодом и тестами S-2
   сохраняется буквально).
5. Новое действие `RELEASE_FROM_SLOT { id }` (или это же — часть логики `pickUp`-колбэка, см.
   ниже) — атомарно ставит `storageSlotId = null` в момент, когда предмет берут в руку из шкафа.
   Технически это может быть отдельным действием, вызываемым `onPickUpFromSlot`-колбэком из
   провайдера, ЛИБО тем же `SET_ITEM_TRANSFORM` с `storageSlotId: null` и неизменной
   позицией/поворотом — выбор конкретной формы уточняется на этапе кода, суть (атомарность,
   слот освобождается в момент перехода в Held) фиксирована.
6. `createInitialState()`: `flask-1` создаётся с `position`/`elevation`, равными координатам
   слота `cabinet-2-slot-1` (или какой выбран, см. раздел 7), и `storageSlotId:
   "cabinet-2-slot-1"`, вместо `[1.2, 0.6]` на столе с `storageSlotId: null`. `cabinets: [{id:
   "cabinet-2", isOpen: false}]`. Остальные предметы — `storageSlotId: null`, без изменений.
7. Новые методы контекста: `toggleCabinet(id)`, а также способ атомарно писать
   `storageSlotId` при взятии/возврате (см. пункт 5).

**Не меняются**: `Container`/химия/`MOVE_ITEM` (кроме уже сделанного в S-2)/`ROTATE_ITEM`/старый
drag — ноль строк.

## 7. Выбор конкретного шкафа для POC — требует проверки камеры (риск №1)

Из 4 существующих шкафов (`x ∈ {-4.6, -3.0, 3.0, 4.6}`, все `y=1.8`, у задней стены) нужно
выбрать один, реально видимый и наводимый в текущих ограничениях камеры
(`minAzimuthAngle=-π/2.8`, `maxAzimuthAngle=π/2.8`, `minPolarAngle=π/7`, `maxPolarAngle=1.42`,
`minDistance=2.2`, `maxDistance=7`, `target=[0,0.1,0]`). **Не проверено геометрическим расчётом
до конца** — рекомендация: начинать реализацию с ЖИВОЙ проверки, какой из 4 шкафов реально
попадает в кадр при разных допустимых углах/дистанциях (скорее всего один из внутренних, `x=-3.0`
или `x=3.0`, а не крайних `±4.6`), и только затем фиксировать выбор в `CABINET_REGISTRY`. Если
окажется, что НИ ОДИН шкаф не помещается в текущие ограничения камеры — потребуется либо
чуть расширить `maxPolarAngle`/`minDistance` (изменение `ChemistryCanvas`, не логики
взаимодействия — отдельно согласовать, а не тихо менять), либо перенести POC-шкаф пониже/ближе.
Это первое, что нужно проверить на практике, прежде чем писать основную логику.

  - Подсказка (`InteractionPrompt`) получает третий вариант текста для сфокусированного шкафа

## 11. Риски

1. **Достижимость шкафа камерой** — см. раздел 7, требует живой проверки в первую очередь.
2. **`setFocused` теперь параметризован `kind`** — единственное изменение публичного API
   провайдера, которое затрагивает уже написанный код Stage S-1/S-2 (`pointerHandlers.onPointerOver`
   внутри `useInteractable` вызывает `setFocused(id)` без указания kind) — нужно обновить ЭТОТ
   вызов на `setFocused(id, "item")`, иначе не скомпилируется/не будет проходить старые тесты.
   Все остальные вызовы (`ContainerMesh`/`StockBottleMesh`) идут через `useInteractable`,
   их менять не нужно — правка в одном месте.
3. **`elevation` — новое обязательное поле типа** — при добавлении нужно проставить его во ВСЕХ
   местах, где сегодня создаются `ContainerItem`/`StockBottle` (`createContainerItem()`,
   `createInitialState()` для 6 бутылок) — иначе TypeScript не даст собраться (это хорошо,
   заставит не забыть ни одного места).
4. **Генерическая логика "вернуть в любой открытый шкаф со свободным слотом"** — при ОДНОМ слоте
   на POC-шкаф пока что эквивалентна "вернуть именно во флаконный шкаф", разница появится только
   когда шкафов/слотов станет больше (следующие стадии) — заложено с самого начала, чтобы не
   переписывать при росте.
5. **Дверь-хитбокс должен быть достаточно большим/удобным для наведения** на типичной дистанции
   камеры — тюнится визуально при реализации, как и все остальные размеры хитбоксов в проекте.

  - повторный `E` на открытом сфокусированном шкафу (ничего не держим) → закрывает;

  position/rotationY, без `elevation` — ведёт себя как раньше (регрессия на S-2); предмет внутри
  закрытого шкафа (`findCabinetContainingPosition` возвращает id, `cabinet.isOpen === false`) —
  `useInteractable` для него возвращает `capability: null` даже если он есть в
  `INTERACTABLE_REGISTRY`.
- Ручная проверка: открыть шкаф → колба видна/фокусируется → взять → закрыть шкаф (колба уже в
  руке, не блокируется) → поставить на стол (проверить, что механика Stage S-2 не сломалась) →
  взять снова → открыть шкаф → навестись на него → `E` → колба легла в слот → закрыть → снова
  открыть → колба на месте, фокусируется заново. Отдельно: пока шкаф закрыт, навести курсор на
  то место, где визуально была бы колба — фокус НЕ должен срабатывать.

## 13. Критерии завершения

1. Шкаф открывается/закрывается по `E`, дверь визуально анимируется.
2. Колба внутри закрытого шкафа не фокусируется и не может быть взята.
3. При открытом шкафе колба ведёт себя как обычный Stage S-1/S-2 предмет (фокус/взять/повернуть/
   поставить на стол — без регрессий).
4. Держа колбу, наведение на открытый шкаф со свободным слотом даёт возможность положить её
   обратно через `E`; `Escape` в любой момент возвращает в точку начала текущего pickup-цикла.
5. Остальные предметы (`beaker-1`, `test-tube-1`, 6 бутылок) и остальные 3 шкафа — без изменений
   в поведении.
6. `tsc`/`eslint`/`vitest`/`pytest`/`build` чистые, ручная браузерная проверка без ошибок в
   консоли.
7. Не закоммичено, пока не пройдена ручная проверка и не получено отдельное подтверждение.
